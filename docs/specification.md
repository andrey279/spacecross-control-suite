
# План разработки защитно-атакующей экосистемы для Minecraft (OpenComputers)

## 1. Введение и контекст
- **Версия Minecraft**: 1.7.10
- **Тип сервера**: Анархия (требует максимальной автономности, отказоустойчивости и защиты от несанкционированного доступа).
- **Ключевые моды**: OpenComputers, WarpDrive, OpenModularTurrets, RFTools, EnderIO, NuclearCraft, ThermalExpansion, OpenSecurity, Computronics.

## 2. Архитектурные принципы (Preconditions)
1. **Среда выполнения**: Первоначальное предположение - работа под управлением OpenOS. Допускается кастомизация для оптимизации и добавления низкоуровневых хуков, однако в таком случае модификация должна быть вынесена в отдельный компонент. Следует предполагать использование стандартного Lua BIOS. Если же все-таки потребуется модификация EEPROM - требуется обоснование, почему того же эффекта нельзя добиться путём модификации OpenOS.
2. **Аппаратно-независимый уровень (HAL)**: Управление внешними системами осуществляется строго через единую прослойку HAL. Это позволяет менять моды без переписывания высокоуровневой логики.
   - **Щиты**: RFTools (Shield Manager), WarpDrive.
   - **Турели**: OpenModularTurrets (с поддержкой базовых методов `toggle()`/`setMode()` для совместимости с другими модами).
   - **Энергобуфер**: Конденсаторы EnderIO (с абстракцией под другие буферы, например, из Mekanism или IC2).
   - **Источники энергии**: Энантиоморфный реактор WarpDrive, ядерный реактор NuclearCraft, термоэлектрические генераторы ThermalExpansion.
3. **Распределённая архитектура**: Из-за большого количества компонентов управление физическими системами может делегироваться отдельным микрокомпьютерам/контроллерам. Связь с главным компьютером корабля обеспечивается через **сетевые карты (Network Card)** или **связанные карты (Linked Card)** in-game. Соответственно, необходима раелизация адресации и обнаружения компьютеров в сети. Вместе с тем, должна быть возможность запускать компоненты на одной машине.
4. **Общая шина событий**: Требуется общая шина сообщений (реализующая передачу сообщений как в рамках одного компьютера, так и по сети).
5. **Разделение компонентов**: Каждый из разрабатываемых компонентов должен быть как минимум в одном или нескольких отдельных .lua файлах, для упрощения разработки и переиспользования.

## 3. Детальный план разработки по модулям

### 3.1. Модуль HAL (Hardware Abstraction Layer) и система драйверов
- **Задача**: Унификация API для разнородного оборудования через паттерн "Реестр драйверов" (Driver Registry), исключающий использование громоздких условных конструкций (`if/else` или `match`) в основной бизнес-логике.
- **Архитектура драйверов**:
  1. **Изоляция в файлах**: Каждый тип оборудования (или мода) реализуется в отдельном `.lua` файле в директории `drivers/` (например, `drivers/enan_reactor.lua`, `drivers/nc_reactor.lua`, `drivers/rftools_shield.lua`).
  2. **Единый контракт (API)**: Каждый файл-драйвер обязан возвращать таблицу (или метатаблицу с `__index`), реализующую строгий набор унифицированных методов. Например: `init(component_proxy)`, `getEnergyLevel()`, `turn_off()`, `isOperational()`.
  3. **Реестр (`drivers.lua`)**: Центральный модуль, который:
     - Импортирует и регистрирует доступные модули драйверов при запуске.
     - При старте (или при событии `component_added`) сканирует систему через `component.list()` и создает **отдельный экземпляр (instance)** соответствующего драйвера для *каждого* найденного компонента, передавая ему `component.proxy`.
     - **Пример**: При обнаружении 2 энантиоморфных реакторов WarpDrive и 1 реактора NuclearCraft, реестр создаст и сохранит в своей внутренней таблице 2 независимых экземпляра `enan_reactor_driver` и 1 экземпляр `nc_reactor_driver`, каждый из которых "знает" только свой адрес компонента.
  4. **Массовое и точечное управление**: Высокоуровневые команды (например, `hal.power.turnOffAll()`) реализуются путем простой итерации (цикла) по всем зарегистрированным экземплярам драйверов и вызова их унифицированного метода (например, `driver:turn_off()`). Специфичная для конкретного мода логика инкапсулирована исключительно внутри этого метода драйвера.
- **Динамическое обнаружение**: При событии `component_removed` соответствующий экземпляр драйвера корректно удаляется из реестра. При `component_added` — создается новый экземпляр.
- **Изоляция сбоев**: Если вызов метода у одного из драйверов вызывает ошибку (например, блок сломан), HAL должен перехватить её (через `pcall`), залогировать как `ERR_COMPONENT_UNREACHABLE` для конкретного экземпляра, и **продолжить** выполнение цикла для остальных драйверов, не роняя всю систему.

### 3.2. Система автопилота (Переписывание)
- **Проблема текущей версии**: Баги с деактивацией лишних ядер (см. [WDShipController](https://github.com/Umaler/WDShipController)).
- **Новая архитектура**:
  1. **Демон управления ядрами (`core_daemon.lua`)**: Работает в фоне постоянно, отслеживает событие остывания ядра и корректно его деактивирует через `event.listen`.
  2. **Модуль навигации и UI (`autopilot_core.lua`)**: Модульная структура, UI вынесен в отдельный плагин. Поддержка интеграции с внешними системами.
  3. **Механизм блокировки (Mutex)**: Использование файла-блокировки (например, `/tmp/autopilot.lock`) с записью PID процесса. При попытке запуска второй программы она проверяет файл и, если процесс жив, получает ошибку `EBUSY` (Resource busy).
- **Интеграция в систему**: Автопилот должен ипользовать разрабатываемые системы, однако должен быть слабо связан (loosely coupled) с ядром корабля через шину событий. Его полное отключение или замена на внешнее управление не должны вызывать ошибок в работе систем жизнеобеспечения (щиты, энергия).
- **Модульность**: В автопилот должно быть достаточно просто добавить новые модули, управляющие автопилотом (например, управляющий модуль программы из 3.4).

### 3.3. Автономный спутник и система минирования
- **Базовый функционал**: Отправка heartbeat-сигнала каждые 10 секунд через интернет-карту на удалённый сервер.
- **Режим "Мина"**:
  1. Подсистема обнаружения: сканирование игроков/кораблей в радиусе (через `warpdrive.radar` или кастомную функцию `FindTargets`, опирающуюся на HAL).
  2. Проверка по Whitelist (данные подгружаются с сервера, и записываются в зашифрованном виде (если есть в наличии encryption модуль из OpenSecurity, в противном случае ничего не должно сохраняться) для последующего использования в случае недоступности сервера).
  3. **Режим атаки**: Отправка алерта на сервер. *Вариант А*: инициация прыжка к цели и подрыв. *Вариант Б*: расчёт вектора до цели, активация 6 вспомогательных зарядов для направленной ударной волны, затем подрыв центрального заряда.

### 3.4. Программа автоматической установки структур (второстепенно)
- **Логика**: Загрузка маршрута → Вызов API автопилота → Запуск процедуры развёртывания (дроны/механизмы) → Подтверждение установки → Следующая точка.
- **Требование**: Структура может иметь собственный компьютер (например, для мин), в который необходимо после/во время сборки структуры загрузить программу управления.

### 3.5. Демон обнаружения игроков (Entity Watcher)
- **Источники данных**: EntityDetector (OpenSecurity) или Radar (Computronics).
- **Функционал**: Работает как фоновый демон. Предоставляет API для опроса другими модулями (например, для визуализации через OpenGlasses, по аналогии с [OC_GlassesMagicEye](https://github.com/Umaler/OC_GlassesMagicEye/blob/main/meye.lua) и для реализации "сигнализации").

### 3.6. Управление системами корабля и безопасность
- **Автоматическое энергопитание**: Сбор телеметрии, динамическое управление реакторами. Приоритетное отключение нагрузок при дефиците: 1) Дорогостоящее производство, 2) Основное производство (если нет `owners`), 3) Маскировка и второстепенные модули.
- **Матрица доступа**: Каждое событие ввода проверяется на наличие ника игрока. Существуют списки `owners` и `admins`.
- **Автоматическое самоуничтожение**: Срабатывает при совпадении **любого** из следующих условий (настраивается в конфиге):
  1. Обнаружен игрок, не входящий в списки `owners` или `admins`, при этом на корабле отсутствует онлайн хотя бы одного `owner` (для `admins` отправляется только критическое уведомление, без подрыва).
  2. Потеря heartbeat-связи с доверенным управляющим сервером дольше заданного таймаута (при включенном режиме "Scorched Earth").

### 3.7. Удалённое управление и сетевая безопасность
- **RPC-шлюз**: Все внешние вызовы проходят через единый порт. Обязательная проверка клиентского сертификата (асимметричная криптография через OpenSecurity).
- **SSH-подобный демон**: Проксирует вызовы к компоненту `gpu`, рендерит в виртуальный буфер, сжимает и передаёт по сети. Клиентская часть работает на чистой OpenOS.
- **Подключение к CnC серверу**: Поскольку OpenOS не допускает входящих интернет-соединений, то соединение должно быть установлено от in-game компьютера к real-life серверу.

### 3.8. Логирование и мониторинг
- **Архитектура**: Выделенный асинхронный демон-логгер.
- **Функционал**: Запись событий управления, доступа, обнаружений, сбоев, энергии, перемещений.
- **Интеграция**: Discord Webhook (напрямую или через Pipedream) для передачи важных сообщений.
- **Безопасность логов**: Локальное резервное копирование на HDD. При потере связи с real-life сервером логи копятся локально. После восстановления связи и успешной передачи на сервер локальные файлы удаляются. Все локальные файлы логов шифруются асимметричным шифрованием (OpenSecurity) для защиты от чтения при физическом захвате HDD.

### 3.9. Сетевое обеспечение
- **Адресация**: Адресация должна быть основана на component address сетевой карты.
- **API**: Требуется API, предоставляющий следующие функции:
  1. Broadcast message (как с отдельной сетевой карты, так и по всем из них)
  2. Отправка сообщения на конкретный адрес (хотя, в основе все сообщения являются broadcast, принимающие стороны должны быть способны фильтровать их).
  3. Все raw сообщения должны обрабатываться, в них должен читаться заголовок, содержащий адресата, и если адресат совпадает (или сообщение - broadcast), то должен генерироваться event, содержащий порт и payload.
  4. Отслеживание доступных хостов в сети в формате:
  ```
  {
    "host_name": str,
    "address": str,
    "type": [list of str|nil], -- i.e. {[1] = "reactors_controller", [2] = "capacitors_controller"}
    "description": [str|nil]
  }
  ```
  Соответственно, требуется примитивный Discovery-протокол.
  
### 3.10. Шина сообщений
- **В рамках компьютера**: все сообщения должны передаваться (возможно, просто генерировать event?).
- **В рамках сетевого взаимодействия**: должна быть конфигурация whitelist/blacklist передавать-ли сообщение, и передавать ли по конкретной сетевой карте.
- **Как принимающиая сторона**: Шина должна читать сообщения от сетевого обеспечения (3.9) и генерировать локальное сообщение.
- **Формат сообщения**:
  ```lua
  {
    proto_version = 1,
    msg_type = "cmd" | "event" | "heartbeat",
    src_addr = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx" | nil, -- nil if localhost
    dst_addr = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx" | "*" | nil, -- * для broadcast, nil - localhost
    port = 27015,
    payload: str -- сериализация/десериализация пусть производится на стороне клиента
  }
  ```
  
### 3.11. Автообновление
Требуется сервис обновления компонентов. 
1. **Локальная сеть**:
  Если на компьютере есть интернет-карта - то по команде (например, по системному таймеру) локальные компоненты должны быть обновлены, затем, если реализована сетевая составляющая:
  1. Broadcast-сообщение об обновлении систем
  2. Каждый клиент, если у него есть интернет-карта - сам себя обновляет, если нет - сообщает о себе инициирующему хосту: какие компоненты на нем установлены.
  3. Инициирующий компьютер собирает то, какие компоненты требуют обновления - и передает их по сети через broadcast сообщения (чтобы, если на нескольких компьютерах установлены одни и те-же компоненты, не передавать их несколько раз).
2. **Атомарность обновления**: Скрипт автообновления должен работать по принципу:
  1. Скачать новые файлы во временную директорию (например, /tmp/update/).
  2. Проверить синтаксис Lua (loadfile).
  3. Только после успешной проверки заменить основные файлы в рабочей директории.
  4. Выполнить ```machine.reboot()```.
3. **Проверка версий**:
  Версии компонентов должны храниться в отдельном манифест-файле, который генерируется на ГитХаб на основе хешей коммитов. Формат файла:
  ```lua
  {
    {
      ["ReactorController"] = {
        version = "1.1",
        files = { "file_1.lua", "file_2.lua", "directory/file_3.lua" }
      },
      ["Autopilot"] = { ... }
    }
  }
  ```
  
### 3.12. Пользовательский интерфейс (UI Framework)
Для всех не-автономных систем требуется реализация единого фреймворка пользовательского интерфейса, работающего строго по следующим принципам:

1. **Архитектура MVC (Model-View-Controller)**:
   - **Model (Модель)**: Данные и бизнес-логика всегда находятся на *целевом компьютере*, который физически управляет компонентом (например, компьютер, управляющий реактором). Не забываем, что целевым компьютером может выступать и локальный, если на нем установлен и запущен соответствующий компонент.
   - **View + Controller (Представление и Управление)**: Компьютер с интерфейсом выступает исключительно в роли клиента. Он отправляет команды (Controller) и отображает полученные данные (View). Он не хранит и не принимает решений о состоянии системы.

2. **Управление вкладками и рендеринг (Full Redraw)**:
   - **Отсутствие кэширования состояния**: Фреймворк **не сохраняет** и не отслеживает состояние неактивных вкладок. 
   - **Полная перерисовка**: При переключении на вкладку (или при первом открытии) инициируется запрос актуального состояния к Модели, после чего вкладка отрисовывается с нуля. Это полностью исключает необходимость реализации сложной логики применения "дельта-изменений" (diffing) при возвращении на вкладку.
   - *Оптимизация*: Для снижения нагрузки на `call limit` при полной перерисовке, статические элементы интерфейса (рамки, фоны, заголовки) должны отрисовываться отдельным методом, который вызывается только при инициализации или изменении разрешения экрана, в то время как динамические данные (текст, прогресс-бары) перерисовываются полностью при каждом переключении или обновлении тика.

3. **Поддержка нескольких GPU и мониторов**:
   - Фреймворк должен поддерживать привязку конкретных экземпляров вкладок или целых UI-панелей к конкретным адресам GPU (`gpu.bind(address)`).
   - Это позволяет, например, вывести панель мониторинга щитов на один монитор, а панель управления энергопитанием — на второй, используя вычислительные ресурсы одного UI-компьютера.

4. **Децентрализация и динамическое подключение**:
   - UI-компьютер **не является** обязательным центральным узлом ("единой точкой отказа").
   - Он работает как универсальный клиент: пользователь выбирает доступные в локальной сети компоненты (например, 2 контроллера реакторов и 1 контроллер щитов), и выводит соответствующие данные (при этом данные из разных компьютеров с одними и тем же компонентом должны объединяться).

## 4. Тестирование

### 4.1 Типы тестов
Для каждого компонента необходимо максимально возможное юнит-тестирование с моками/стабами. Архитектура тестов должна позволять запускать их как внутри игры, так и в стандартном интерпретаторе Lua 5.2/5.3 на ПК разработчика. Для этого все зависимости от ```component``` и ```os``` должны быть изолированы через слой моков (stubs), что позволит проводить 95% тестов мгновенно на ПК, а в игре запускать только интеграционные тесты.

### 4.2 Файловая структура
Тесты должны быть расположены в директории "tests", расположенной рядом с файлом тестируемого объекта. Моки/Стабы - в поддиректории "stubs". Пример:
```
component_name
|-tests
| |-stubs
| | |-component_file_one_test_stubs.lua
| | 
| |-component_file_one_test.lua
| |-component_file_two_test.lua
|
|-component_file_one.lua
|-component_file_two.lua
```

### 4.3 Формат тестов
Каждый тест - функция, не принимающая аргументов, и возвращающая таблицу:
```lua
{
  "status": bool, -- true if success
  "error_code": [str|nil] -- nil if success, otherwise description of the failure
}
```
В конце файла должен быть объявлен массив ```all_tests```, каждый элемент которого - таблица:
```lua
{
  "test_name": str,
  "test": function -- test itself
}
```
Тело теста НЕ ДОЛЖНО быть реализовано внутри объявления таблицы, а должно быть реализовано выше в функции с таким же названием, что указано в поле "test_name".

### 4.4 Запуск тестов
Должна быть единая утилита, которая запускает все возможные тесты по умолчанию, либо же только те, которые указаны в параметрах запуска (если таковые есть). Соответственно, данная утилита должна обновляться после добавления каждого из тестов, чтобы в ней содержались пути до каждого из компонентов, а уже в директории каждого из компонентов - искать директорию tests. После прогона тестов должна выводится статистика: сколько тестов из всего кол-ва тестов пройдено успешно, сколько тестов упало, сколько тестов вернуло неудачу. Соответственно, должна формироваться таблица <название файла | название теста | статус | {строка ошибки/строка возврата, если функция вернула неудачу/строка Success", если тест завершился удачно}>. Соответственно, столбец статусов (и только он) должен быть раскрашен в:
- красный - если функция упала
- желтый - если функция вернула ошибку
- зеленый - если success

## План реализации
Разработка должна вестись в следующем порядке:
1. Ключевые системные компоненты
  - Утилита для автотестов
  - HAL (его API, реализации - по ходу надобности)
  - Логгинг
  - Локальная часть шины
  - Утилита обновления системы (без сетевой составляющей, без проверки версий - просто установка файлов из самого последнего коммита с ветки main)
  - Компонент интерфейса
2. Ключевые оборонительные компоненты
  - Детекция игроков
  - Система самоуничтожения
3. Важные на первых порах системы:
  - Автопилот
  - Управление энергопитанием (реакторы и включение/отключение энергоёмких систем)
4. Вторичные системные компоненты
  - Сетевая часть шины
  - Сетевое обеспечение
  - Удаленное управление и системы безопасности
  - Оставшиеся компоненты утилиты обновления системы
5. Второстепенные системы
  - Система автоматической установки структур
  - Программа для спутников

В ходе разработки читай и сохраняй в файле current_state.txt состояние разработки (на каком пункте плана реализации остановка остановилась, в каком состоянии находится каждый из разрабатываемых компонентов).
