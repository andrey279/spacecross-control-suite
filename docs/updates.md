# Компонентные версии и обновления по LAN

Реализованы генератор версий на GitHub, локальная установка профиля компонентов
и распределённый updater. Проверки на ПК используют настоящие Git-репозитории и
четыре независимых Lua app instances со стабами оборудования. Реального GitHub
репозитория/deployment и игрового прогона ещё нет.

## Генерация релиза

`components.json` задаёт владельца файлов и зависимости. Более длинный путь
побеждает короткий; неоднозначность отклоняется. Все `*/tests/*` принадлежат
компоненту Tests. Текущие группы: Core, Autopilot, Power, Entity, Defense,
Terminal, CnC, Tests. Core содержит общий runtime/HAL/network/RPC/UI и
`defense/access.lua`; Tests зависит от всех доменных групп. При добавлении новых
доменных компонентов каталог и зависимости Tests нужно дополнять.

`tools/manifest.py` читает Git objects выбранного commit и проверяет соответствие
committed install.list всему committed Lua tree. Dirty worktree не попадает в
артефакт. Версия компонента — полный SHA последнего коммита, затрагивавшего его
файлы или components.json. Удалённые исторические файлы тоже учитываются.
Для каждого текущего файла записаны SHA256 и размер; зависимости проверяются
на существование и циклы. Пример команды в настоящем checkout:

```sh
python3 tools/package.py --check
python3 tools/manifest.py --revision HEAD --out dist
lua5.2 tools/check_manifest.lua dist/components.sc
```

Этот рабочий каталог пока не является Git checkout. Тест создаёт отдельный
временный репозиторий из текущих исходников и проверяет каталог, Python→Lua codec
и синтаксис генерируемой таблицы; он не создаёт фиктивный SHA для deployment.

Workflow `.github/workflows/release.yml` на push main генерирует и публикует
`components.sc` и `components.lua` в release `spacecross-<GITHUB_SHA>`.
Повтор workflow сравнивает существующие assets, не заменяя их другими байтами.
Workflow написан, удалённо не запускался. Частично опубликованный release требует
устранения ошибки публикации; клиент не переходит к непроверенному fallback.

Читаемый формат соответствует таблице из ТЗ:

```lua
return {{
  Autopilot = {version = "<40-character-commit>", files = {"spacecross/autopilot/autopilot_core.lua"}, requires = {"Core"}}
}}
```

Runtime получает `components.sc` — data-only сериализацию с v/revision/components/
files. Полученный текст Lua никогда не выполняется для разбора манифеста.
Сначала latest main разрешается в один SHA; asset и исходники привязаны к нему.
Если main уже обновлён, а CI ещё не опубликовал asset, проверка завершается ошибкой
и прежнее поколение остаётся активным.

## Профиль и атомарная установка

`update.components` задаёт установленные корневые компоненты, например
`{"Core","Autopilot","Power"}`. Зависимости добавляются автоматически, Core
присутствует всегда. Профиль должен включать включённые в основном конфиге службы.
При отсутствии настройки LAN service сохраняет предыдущий профиль; первая
установка без профиля выбирает все компоненты. Для запуска тестов после установки
нужен компонент Tests, который добавляет необходимые ему модули.

Файлы с совпадающими хешами повторно используются из активного поколения.
Отсутствующие/изменённые файлы скачиваются; лишние файлы не копируются в новое
поколение. Если профиль, версии и файлы уже совпадают, публикации/перезагрузки нет.
Поэтому изменение неустановленного компонента не заставляет менять своё поколение.

Имя поколения — SHA исходников + 128-bit префикс SHA256 canonical списка выбранных
компонентов (всего 73 символа). Это позволяет держать разные профили одного commit
без изменения стабильного bootstrap. Полные SHA256 файлов проверяются отдельно.
В поколении сохраняются `COMPONENTS`, `PROFILE` и READY; metadata входит в
проверку неизменяемости готового поколения. До переключения проверяются размеры,
хеши и Lua syntax. После записи active.new выполняется одна replace-rename на
том же HDD. Cancellation проверяется также непосредственно перед этим rename.

На filesystem/root действует общая lease для разных updater instances; LAN
сеанс держит её до завершения раздачи. Standalone updater получает EBUSY, если
тот же root уже обновляется. Native fs wrappers разделяют одну lock identity,
в независимых PC stubs namespaces раздельные. Process adapter позволяет убрать
резервирование умершего процесса. Ошибка и stop освобождают lease; stop/start
не возобновляет старую приостановленную установку.

Успешная changed-установка вызывает `computer.shutdown(true)` через runtime.
Координатор откладывает перезагрузку, чтобы сначала обслужить LAN. Stop после
уже выполненной публикации не откатывает active; новое поколение используется
при следующем запуске. Готовые поколения и cache сохраняются, автоматической
ротации старых каталогов пока нет.

## Конфигурация и доверие

Для LAN включить `network`, `rpc` и `update.enabled`. Нужны client+server identity,
стандартный общий logical RPC port 27016 и SHA256 provider. Сейчас runtime использует
SHA256 настроенного RPC crypto; для автономного локального versioned updater
можно задать `update.hashAddress` компонента с raw-byte sha256. SHA256 существует
и у OC Data Card Tier1; для самого certificate RPC нужен прежний Tier3 provider.
Фактические лимиты Data Card/паузы и таймауты сборки нужно проверить в игре.

Сертификату каждого получателя нужны client grants:

```json
{"_update":["describe","manifest","need","status","done"]}
```

На координаторе `update.peers` перечисляет точные machine subjects, которым
разрешены эти внутренние методы. Owners также допускаются. Source/receiver
берутся из verified RPC context, а не из args. У получателя в
`update.publishers` задан map `publisher component address -> certificate subject`.
Сертификат издателя должен иметь server usage, адрес этой карты и grant
`_update.publish` (либо wildcard). Это отдельное полномочие установки кода;
machine subject не требуется добавлять в список игровых owners.

Для ручного запуска `update.check` по модели дополнительно требуется player
owner-role. Admin не может запустить проверку, подставив player в args.
Настройки и пример находятся в `config.example.lua`.

Вкладка Updates показывает состояние целевого сервиса и кнопку Check main + LAN.
Универсальный UI может выбрать эту модель через Network, как другие удалённые
командные модели. Из CnC команда ставится обычным `server.control enqueue` с
model `update`, action `check`; сертификат оператора должен разрешать этот вызов.
Периодический запуск задаётся `update.checkInterval` в секундах.

`bin/update.lua` — отдельная локальная установка, когда раздача не нужна:
с `versioned=true` он проверяет hashes/profile из release asset. Legacy-режим
`versioned=false` сохраняет первоначальную установку полного install.list по SHA
и syntax checks; проверки хешей/LAN в нём нет. Для LAN команда адресуется
работающему update model, запуск второго полного приложения не требуется.

## LAN-сеанс

1. Интернет-хост фиксирует latest main, устанавливает свои компоненты и публикует
   свой active с отложенным reboot. Затем сообщает session ID через broadcast offer.
2. Offer является подсказкой. Получатель сначала проверяет allowlist адреса,
   делает свежий challenge-bound RPC describe и сверяет CA/сертификат/subject/
   publish grant. Старый записанный offer не устанавливает код без живого сеанса.
3. Манифест передаётся подтверждёнными RPC-страницами до 4096 байт и проверяется
   по digest из describe. При наличии HTTP-интернет-карты клиент скачивает этот
   же release asset сам и сравнивает digest; main повторно не разрешается.
4. Каждый клиент сообщает выбранные компоненты и отсутствующие файлы. Клиент
   с интернетом сообщает independent mode и скачивает файлы сам. Остальные
   заявки объединяются в общую очередь координатора.
5. Общий файл передаётся один раз за проход, независимо от числа запросивших
   клиентов. Блоки до 4096 байт идут broadcast через service update на том же
   logical port 27016, используя существующие framing/fragmentation транспорта.
   Broadcast на нескольких картах физически повторяется по одному разу на карту.
6. Получатель принимает только нужные пути текущего подтверждённого сеанса.
   Блоки сами не являются RPC-вызовами: целый файл сверяется с authenticated
   manifest. Подмена/неполный файл не попадает в active. До двух незавершённых
   файлов собираются в RAM, готовый проверенный файл сохраняется в HDD cache.
7. При потере/порче блоков клиент запрашивает status; повтор назначается после
   завершения соответствующего прохода. Запросы ремонта одного файла также
   объединяются. Счётчик rounds и последние needs делают повтор запроса идемпотентным.
8. Клиент атомарно публикует полный выбранный профиль, отправляет done и
   перезагружается. Координатор ждёт клиентов и небольшой grace для ответов;
   при distribution timeout завершает свою уже опубликованную установку reboot.
   Узел с неполной загрузкой сохраняет прежний active и сообщает failure локально.

Готовый byte cache расположен в `<root>/cache/<source SHA>/...`; каждый раз
проверяется digest. Версии разных компонентов, unselected файлы и live snapshots
оборудования в UI не кэшируются этим протоколом. READY и active принадлежат
атомарному updater, broadcast не записывает их напрямую.

Основные настройки: interval 0.1 s, collectTime 3 s, quietTime 1 s,
maxCollectTime 30 s, timeout 120 s, maxClients 64, maxRepairRounds 3,
repairInterval 2 s, finishGrace 1 s. Hash/source/metadata ошибки, неизвестные
компоненты, cycles, unsafe paths, mismatch и cancellation отклоняются. Новый
клиент после закрытия регистрации ждёт следующей инициированной раздачи.
После неуспеха можно повторить Check: готовые поколения и проверенный cache
переиспользуются; частично загруженный код не активируется.

Пределы манифеста: 64 компонента, 4096 файлов, 131072 serialized bytes,
1 MiB на файл и 16 MiB суммарно. Runtime codec имеет и предел сложности;
слишком сложный объект отклоняется, даже если его byte size ещё мал.
Скорость, RAM/disk и достаточность таймаутов на настоящей сборке OC не измерены.
Проверки в игре добавлены в [ingame_checks.md](ingame_checks.md), пункты 29–33.
