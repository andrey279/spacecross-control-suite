# Удалённый терминал

`terminal.enabled` запускает демон с отдельным программным GPU для каждой
сессии. Стандартный `/bin/sh` OpenOS работает в отдельном процессе и PTY;
на сервере физические GPU и экран не нужны. Клиенту нужны обычный OpenOS,
GPU/экран, клавиатура, Network/Linked Card и настроенная RPC identity с Data Card.
Используются те же transport и logical RPC port 27016; новый аппаратный порт
не открывается. Это собственный протокол SpaceCross, с SSH-клиентом он несовместим.

## Настройка

На сервере включить `network`, `rpc`, `terminal` в `config.example.lua`; owner
должен быть в `owners`. Параметр `terminal.program` — абсолютный путь программы
без аргументов, по умолчанию `/bin/sh`. Клиент не может выбирать другой путь.
Обычный shell предоставляет владельцу полный доступ к ОС и оборудованию.
Поэтому все действия терминала дополнительно требуют owner-роли; Admin даже
с широкими grants не получает shell.

Выпустить ключи и сертификаты по [rpc.md](rpc.md). Server certificate должен
иметь usage `server` и адрес серверной карты. Client certificate — usage
`client`, subject с ником owner и адрес клиентской карты. Для него grants:

```json
{"terminal": ["open", "frame", "chunk", "input", "resize", "close"]}
```

Скопировать `config.client.example.lua` в `/etc/spacecross-client.lua`, настроить
карты, приватный ключ owner, его сертификат и CA public key. На клиенте из корня
проекта выполнить:

```sh
bin/remote.lua SERVER-CARD-ADDRESS Owner /etc/spacecross-client.lua
```

Клиент запускает только транспорт и RPC; корабельные контроллеры на клиентском
компьютере не запускаются. Все входящие события проверяются по нику и адресам
экрана/его клавиатур. Ник берётся из события, затем проверяется на клиенте;
на сервере actor независимо берётся из сертификата. Без ника ввода нет.
Ctrl+C направляется в удалённую сессию; Ctrl+Alt+Q закрывает соединение и shell.
После выхода или ошибки клиент восстанавливает содержимое, разрешение,
foreground/background, глубину и viewport своего экрана.

Payload RPC подписан, но не зашифрован: это относится и к тексту экрана и вводу.
Пароли и секреты, набираемые в таком терминале, не получают конфиденциальности
от механизма подписей. Отдельное шифрование журналов этого не меняет.

## Разделение процессов OpenOS

`terminal/openos_scope.lua` использует штатные `term.internal.open`, process
data window и scheduler hook `data.pull`, который предоставляет библиотека
`thread`. Короткая установка PTY временно привязывает только программный GPU
и восстанавливает прежний объект окна; вызовов физического GPU и ожидания
событий в этой части нет. Это поддерживает и headless-сервер.

Каждый thread получает своё окно, копии переменных/aliases, клавиатурные
состояния и ограниченную очередь ввода. В глобальную очередь отправляется
только `spacecross_terminal_wake, sessionId`. Raw remote key/touch/clipboard и
`interrupted` туда не публикуются. Ctrl+C преобразуется в частный `interrupted`
до проверки глобального interrupt в OpenOS; учитываются оба порядка нажатия
Control и C. Чужие физические клавиши и глобальный interrupt внутри сессии
отфильтровываются.

Состояния `keyboard.pressedCodes/pressedChars` предоставляются через прокси,
выбирающий таблицы текущего процесса. У root остаются исходные физические
таблицы. Совместимый хук находится целиком в отдельном модуле; файлов OpenOS
и EEPROM он не изменяет. После остановки сессий прокси остаётся установленным
и для процессов без `sc_terminal_keys` прозрачно использует физические таблицы.

Программы получают виртуальный GPU через `term.gpu()` и переданный в environment
`require("component")`: primary GPU/screen/keyboard, list/proxy/invoke направляются
на устройства сессии. Обычные неграфические компоненты доступны владельцу.
Библиотека, ранее сохранившая реальный GPU в своём module cache, может обращаться
к нему напрямую; такую библиотеку нужно адаптировать к `term.gpu()`/передаваемому
прокси. Сессия не является sandbox для программ владельца. Варианты OpenOS без
используемых внутренних API отклоняются; совместимость конкретной сборки должна
быть проверена в игре.

## Буфер и wire format

Программный GPU поддерживает базовые get/set/fill/copy, цвета/палитру,
resolution/viewport/depth и одну виртуальную screen binding. Копирование учитывает
перекрытие и обрезку обеих половин широкого символа; изменение разрешения не
оставляет половины glyph. В OpenOS ширину определяет `unicode.wlen`; запасной
расчёт на ПК покрывает используемые тестами Unicode диапазоны. VRAM API поздних
версий OC не требуется. Квантизация цветов низких глубин не эмулируется побитно.

Кадр `SCT1` содержит u16 big-endian width/height, 16 RGB24 цветов палитры, затем
RLE runs: u16 count и packed cell. Cell — u8 длина glyph в UTF-8, foreground RGB24,
background RGB24, u8 flags, glyph bytes. Биты flags: foreground palette index,
background palette index, wide continuation. Продолжение имеет пустой glyph и
те же цвета, что предыдущая широкая клетка. Лимит glyph — 64 байта; остаток
слишком длинной combining sequence не добавляется. Пустой экран с любым
разрешением до 160×50 занимает 67 байт. Разноцветный текст сжимается слабее.

`frame` фиксирует полный снимок с token; `chunk` читает этот снимок частями до
4096 байт. Новый вывод не изменяет уже закреплённые байты. Следующий `frame`
заменяет token, а обращение по прежнему возвращает `ESTALE_FRAME`. Клиент сначала
получает все части и валидирует размеры, палитру, UTF-8, runs и широкие клетки,
затем полностью перерисовывает экран. Обрыв загрузки и повреждённый кадр не
вызывают частичную перерисовку. Производительность зависит от Data Card, размера
снимка и GPU; интерактивная скорость на реальном OC ещё не измерена.

## API и пределы

Все вызовы проходят через `rpc:request(host, "terminal", action, actor, args)`:

| Action | Args | Результат |
|---|---|---|
| open | width, height | id, width, height, sequence=0 |
| frame | id | token, bytes, width, height, generation, status, sequence |
| chunk | id, token, offset (с 1), length≤4096 | бинарная строка |
| input | id, sequence, events | принятый sequence |
| resize | id, width, height | true |
| close | id | true |

Events: `{name="key_down"/"key_up",char,code}`, `{name="clipboard",text}`,
`{name="touch"/"drag"/"drop"/"scroll",x,y,button}`. Источники и actor создаёт
сервер; поля клиента с ником или адресом источника не используются.
Batch содержит 1–32 события, clipboard до 4096 байт. Batch сначала проверяется
полностью, затем принимается целиком. Счётчик начинается с 1; точный повтор
последнего batch возвращает ACK без повторного ввода, другой batch с тем же
sequence — `ESEQUENCE_CONFLICT`, пропуск — `ESEQUENCE`. Client API сохраняет
pending batch и предоставляет `retryInput()`. CLI при неизвестном исходе
завершает сессию; он не создаёт batch с новым номером автоматически.

По умолчанию: до 4 sessions, до 2 на owner, общий резерв 16000 клеток,
160×50 максимальное разрешение. Резерв на одну сессию равен maxWidth×maxHeight,
включая её последующее изменение разрешения программой. Поэтому с настройками
по умолчанию одновременно работают максимум две сессии. На сессию: один кадр
до 600000 байт, 256 queued events/32768 encoded bytes, один повторяемый batch,
idle TTL 120 s, минимальный интервал frame 0.1 s. Время обновляется только
допустимым владельцем сессии. Локальное удаление owner закрывает её при sweep;
отзыв сертификата прекращает RPC, затем неиспользуемая сессия истекает по TTL.
Закрытие/остановка службы убивает её thread. Остановка shell не останавливает
шину, сеть, автопилот и энергетику. Логируются открытие/закрытие с actor;
keystrokes и содержимое экрана в лог не копируются.

Перед использованием: [ingame_checks.md](ingame_checks.md), пункты 21–24.
