# SpaceCross

Проект для OpenComputers/OpenOS в Minecraft 1.7.10. Рассчитан на стандартный
Lua BIOS и не требует изменений EEPROM. Текущее состояние: [current_state.txt](current_state.txt).

В репозитории находятся HAL, автопилот, питание и защита, сеть Network/Linked
Card, discovery, RPC, удалённый терминал, CnC-сервер, спутники, развёртывание
структур и обновление компонентов. Игровые проверки перечислены в
[docs/ingame_checks.md](docs/ingame_checks.md).

## Проверка на ПК

Из корня проекта:

```sh
lua5.2 run_tests.lua --no-color
lua5.3 run_tests.lua --no-color
lua5.2 run_tests.lua spacecross/hal spacecross/defense
python3 tools/package.py --check
lua5.2 tools/check_syntax.lua
```

Если исполняемого файла Lua нет, но установлена `liblua5.2.so.0`:

```sh
python3 tools/lua.py run_tests.lua --no-color
```

Тесты находятся рядом с модулями в `tests/`, стабы — в `tests/stubs/`.
Общие стабы платформы находятся в корневом `tests/stubs/`.
Новый компонент добавляется в `test_components.lua`. Утилита обнаруживает его
`*_test.lua`, вызывает именованные функции из `all_tests` и различает падение,
возврат неудачи и успех. Несуществующий фильтр и пустой прогон завершаются с ошибкой.
Цвет применяется только к столбцу статуса; `--no-color` отключает ANSI.

Криптографические векторы проверяют HMAC/HKDF и точный формат шифрованного
конверта против независимых результатов Python `cryptography` и `hashlib`.
Для их регенерации: `python3 tools/generate_crypto_vectors.py` (нужен `cryptography`).
Штатный Lua-прогон не требует Python-пакетов.

## Запуск в OpenOS

1. Скопировать проект на HDD, например в `/home/spacecross`.
2. Скопировать `config.example.lua` в `/etc/spacecross.lua` и настроить ники,
   адреса компонентов, драйверы и нужные модули.
3. В корне проекта выполнить `run_tests.lua --no-color`.
4. Запустить `bin/spacecross.lua /etc/spacecross.lua`. Ctrl+C завершает службы.

Без GPU работают HAL, шина, логгер, детектор и оборонительная политика.
UI не владеет состоянием оборудования. Модели находятся на контроллере;
вкладки получают свежий snapshot при каждом открытии/обновлении.
Для нескольких экранов настроить отдельный GPU на каждую панель.
Вкладки переключаются касанием второй строки, прокруткой на ней или стрелками
влево/вправо на привязанной клавиатуре. Активная вкладка остаётся видимой на узком
экране. Ввод проверяет ник и экран.
Кнопки Arm/Disarm доступны только владельцам через модель на контроллере.

Для OpenSecurity Entity Detector добавить драйвер
`spacecross.hal.drivers.opensecurity_detector` и включить `watcher`.
`range` — запрошенный радиус; драйвер учитывает деление аргумента на два в
официальном старом API. Верхняя граница всё равно ограничивается конфигурацией мода.
API возвращает display name; если сервер меняет имена плагинами, сопоставление
со списками доступа нужно проверить в игре.

Альтернативный источник — Computronics Radar. Для upstream-ветки 1.7.10
подтверждены component type `radar`, `getPlayers([distance])` и поля записи
`name`, `x`, `y`, `z`, `distance`; драйвер использует их по умолчанию. Для форков
добавляйте в `drivers` конфигурируемый `computronics_radar` с явными overrides.

Для сбора подтверждённых типов и сигнатур используйте read-only команду
`bin/inspect_components.lua radar os_entdetector`. Она перечисляет доступные
методы и документацию, не вызывая оборудование. Сохраните вывод вместе с
версией сборки; наличие метода не доказывает, что его вызов безопасен или
функционально успешен.

Для исполнительных redstone-каналов добавить драйвер
`spacecross.hal.drivers.redstone`, настроить `defense.channels` и включить `defense`.
Система по умолчанию не взведена. Правило вторжения: подтверждённый посторонний
при отсутствии всех owners. Присутствие любого owner подавляет только это правило.
Admin вызывает критическое уведомление; один admin не вызывает подрыв.
Scorched Earth независимо срабатывает после таймаута доверенного heartbeat.
При неполной телеметрии нельзя доказать отсутствие owner: правило вторжения
остаётся неопределённым. При включённом CnC heartbeat принимает только одноразовое
подтверждение свежего RPC-ответа pinned сервера. Сетевой alive/discovery не является
доказательством. Без CnC можно предоставить отдельный `verifyHeartbeat` адаптер.

## Логи и криптография

`logger:write` ставит запись в ограниченную RAM-очередь. Таймер шифрует её перед
записью на HDD. Файлы `.sealed` переживают перезапуск и удаляются только после
точного подтверждения их ID функцией `upload`. Счётчик `sequence` — открытые
метаданные для уникальных ID, без содержимого событий. Без криптопровайдера
записей на HDD нет; `lastError` показывает причину, `dropped` — переполнение RAM.
При настроенном CnC agent передаёт sealed файлы внешнему Python-серверу.
Удаление требует подписанный receipt с точным ID и digest после SQLite commit.
Discord outbox сохраняет и повторяет важные уведомления независимо от receipt.
Настройка, управление и пределы: [docs/cnc.md](docs/cnc.md). Реальный внешний
сервер и Discord URL не установлены; выполнен localhost Lua↔Python тест.

Официальный OpenSecurity 1.7.10 не предоставляет RSA/ECC:
[исходник Data Block](https://github.com/PC-Logix/OpenSecurity/blob/f2cf1d706a832199f51bb14f47584190706f7cc6/src/main/java/pcl/opensecurity/tileentity/TileEntityDataBlock.java).
Отдельный, явно выбираемый адаптер `spacecross.security.data_card` использует
[OpenComputers Data Card Tier 3](https://ocdoc.cil.li/component:data).
Для форка OpenSecurity можно предоставить другой модуль с контрактом
`new(deps, config) -> {seal = function(plaintext) -> ciphertext}`.

Адаптер Data Card использует эфемерный ECDH P-256, HKDF-SHA256,
AES-128-CBC и HMAC-SHA256 по всему конверту. На корабле хранится только публичный
ключ сервера X.509 DER, приватный ключ не нужен. Конфигурация показана в примере.
Обратная совместимость с реальным игровым компонентом ещё требует проверки.

## Обновление

В конфигурации обновления указать `update.repository` для нужного GitHub-репозитория.
`bin/update.lua` разрешает `main` в конкретный SHA. В versioned-режиме он получает
GitHub release manifest, проверяет SHA256 и устанавливает выбранные компоненты
с зависимостями. `python3 tools/package.py` поддерживает install.list, а
`tools/manifest.py` и release workflow формируют версии из Git commit hashes.

Обновление создаёт поколение на том же HDD в `system/releases/<SHA-profile>`, проверяет
синтаксис всех Lua-файлов без выполнения, записывает READY и переключает файл
`system/active` одним rename. Затем вызывает `computer.shutdown(true)` —
штатный аналог перезагрузки OpenOS. `/tmp` не используется для публикации,
поскольку другой файловый том нарушил бы атомарность rename.
Конфигурация и логи остаются вне поколений. Неуспешная публикация допускает
повторный запуск с проверкой ранее скачанных файлов.

LAN service включается через `update.enabled` вместе с network/RPC. Команда
модели `update.check`, вкладка Updates или таймер обновляют инициатора, затем
рассылают offer. Получатели подтверждают manifest через сертификатный RPC;
узлы без интернета сообщают components и получают общие файлы одной broadcast
раздачей, узлы с интернетом скачивают сами. Издатель проверяется по allowlist
и `_update.publish`, игрок при ручном запуске — по owner-role.
Конфигурация, профили, лимиты и формат: [docs/updates.md](docs/updates.md).

Для запуска поколений скопировать `bootstrap.lua` в стабильное место на HDD
и запускать его. EEPROM менять не нужно. Перед эксплуатацией нужно проверить
replace-rename и сохранность файлов после выключения на конкретной версии OC
и файловой системе сервера. Репозиторий проекта:
https://github.com/andrey279/spacecross-control-suite.

## HAL

`spacecross.hal.drivers` регистрирует определения `{id, types, kind, new}`.
`new()` создаёт отдельный объект для каждого component address. Объект обязан
предоставлять `init(proxy)`, `getEnergyLevel()`, `turn_off()`, `isOperational()`.
Не поддерживаемый метод возвращает `nil, "ENOTSUP"`; ложное булево состояние
без второй ошибки является допустимым результатом. `getEnergyLevel` для
энергооборудования возвращает `{stored, capacity}`. Команды возвращают `true`
либо `nil, error`. `hal:call(address, method, ...)` и `hal:all(kind, method, ...)`
изолируют отказы; авария драйвера получает `ERR_COMPONENT_UNREACHABLE` с адресом.
`component_added` и `component_removed` обслуживаются фоновыми слушателями.

Высокоуровневые физические системы используют только HAL. Системные адаптеры
OpenOS владеют event/filesystem/internet, а UI — привязкой GPU к экрану.
Транспорт, discovery, per-card whitelist/blacklist и проверка сертификатов RPC
реализованы отдельными компонентами.

Для RFTools Shield Projector и его ограничений см. [docs/shields.md](docs/shields.md);
для OMT HAL/model/UI и его границ API см. [docs/turrets.md](docs/turrets.md).
Спутниковый контроллер и автономные deployment gates описаны в
[docs/satellite.md](docs/satellite.md) и [docs/structures.md](docs/structures.md).

## Сетевое обеспечение

Настройка `network` показана в `config.example.lua`. Транспорт поддерживает
`modem` и `tunnel`, broadcast с одной/всех выбранных карт, адресную фильтрацию,
логические порты, фрагментацию, ограниченную сборку и hotplug.
`app.discovery:list()` показывает доступные адреса карт; `app.network` предоставляет
API отправки. Сетевой мост шины включается отдельно через `network.bus.enabled`.

Discovery не даёт прав доступа. Сетевые события пока являются неаутентифицированными
данными. Управление удалёнными моделями проходит через проверку
сертификатов RPC. Автономные модели не исполняют raw-команды сети.
Полный формат протокола, API и фильтров: [docs/network.md](docs/network.md).

## RPC и удалённый интерфейс

`rpc.enabled` требует network, явного криптопровайдера, собственного сертификата
и локального CA public key. Предоставлен адаптер Data Card Tier 3 с ECDSA;
никаких BIOS/OpenOS модификаций не требуется. Сертификат определяет ник actor,
адреса карт и grants; дополнительно проверяются target owners/admins. Повтор
запроса использует одноразовый challenge и не повторяет физическое действие.

Network вкладка позволяет выбирать модели найденных контроллеров после
аутентифицированного запроса их каталога. Снимки остаются на целевых компьютерах,
несколько энергоконтроллеров отображаются вместе. Подписи не шифруют payload;
логирование имеет отдельный механизм шифрования. Реальный OpenOS/Data Card
сценарий пока не проверен. Настройка, PKI-инструменты, формат и ограничения:
[docs/rpc.md](docs/rpc.md).

`terminal.enabled` добавляет отдельные owner-only shell-сессии с программным GPU,
RLE-кадрами и частным вводом. Клиент `bin/remote.lua` работает на обычном OpenOS;
серверу физический GPU не нужен. Ник берётся из сертификата, сессии ограничены
по памяти/вводу/времени. Ctrl+Alt+Q закрывает shell и восстанавливает клиентский
экран. Настройка ключей, конфигурации, протокола и пределы совместимости:
[docs/terminal.md](docs/terminal.md). Проверки адаптера на ПК используют стабы;
реальный shell/GPU в игре ещё не проверен.

## Автопилот

Включить `autopilot.enabled`, добавить драйвер `warpdrive_ship` и указать адрес
`warpdriveShipController`. `coreDaemon.controllers` ограничивает управляемые ядра;
без списка демон управляет всеми зарегистрированными навигационными экземплярами.
Навигация работает с координатами активного ядра в текущем измерении, делит маршрут
на прыжки допустимой длины и учитывает ориентацию корабля.

API: `navigate({x,y,z}, address)`, `setRoute({{x,y,z},...}, address)`, `cancel()`,
`snapshot()`, `start()`, `stop()`. Координаты целые. Следующий прыжок выполняется
после события остывания и проверки новой позиции. При исчезновении контроллера,
нехватке энергии, отсутствии движения или таймауте навигация сообщает ошибку.
Для управляющих расширений есть `registerController(name, handler)` и `control`.
Переходы состояния публикуются через шину на порту 27102.

`core_daemon.lua` подписан на `shipCoreCooldownDone` независимо от навигации.
Неактивное ядро переводится в OFFLINE после остывания, отказ деактивации повторяется.
Событие другого ядра не отключает активное. Отмена прекращает дальнейший маршрут;
уже начатый прыжок может завершиться, после чего демон деактивирует его ядро.
Остановка навигации через её модель/UI сохраняет демон и энергоконтроллер.
Полный выход из приложения останавливает все его службы.

Файл `/tmp/autopilot.lock` содержит числовой ID живого процесса. Стандартный OpenOS
не имеет POSIX PID: изолированный адаптер `runtime/processes.lua` назначает ID и
проверяет живой процесс через `process.info(thread)`. Резервирование общего модуля
защищает от гонки до файлового I/O. Живая блокировка даёт EBUSY, мёртвая заменяется;
повреждённая/нечитаемая не перезаписывается. Смена BIOS или OpenOS не нужна.

UI-плагин хранит целевые координаты на модели контроллера. Кнопки ± изменяют их
на 10 блоков; Go запускает переход, Cancel отменяет маршрут, Stop/Start отключают
и включают саму навигацию. API модели также принимает точные `setTarget`, `navigate`
и `route`. Конфигурация `autopilot.target` задаёт начальную цель.

## Энергопитание

Включить `power.enabled`; настроить `buffers`, `sources` и `loads` в примере.
Реализованы драйверы WarpDrive Enan reactor, EnderIO через стандартный RF-интерфейс,
NuclearCraft 1.7.10 и Thermal-генераторов через RF-телеметрию и проводной redstone.
Enan использует встроенный цикл стабилизирующих лазеров; телеметрия снимает
startup hold. Наличие и питание самих лазеров нужно проверить на корабле.

У разных модов OpenComputers может показывать одинаковый `energy_handler`.
Конфигурируемый драйвер выбирается по адресу: элемент `drivers` может быть строкой
либо `{module=..., options={devices={...}}}`. Все соответствующие экземпляры
независимы. Если одному адресу подходят два драйвера, HAL сообщает
ERR_AMBIGUOUS_DRIVER вместо выбора случайного драйвера.

EnderIO: `enderio_capacitor`, привязать по одному адресу на физический банк.
NuclearCraft: `nc_reactor`, адрес RF-компонента и отдельный redstone-канал
`controlAddress`, `side`. В официальном NC 1.7.10 реактор запускается сигналом HIGH;
нативный `activate()` из новых версий не предполагается. Thermal: аналогичный
`thermal_generator`; redstone-режим машины должен соответствовать её
`onValue`/`offValue`. Это проводное управление через HAL, без выдуманного
термоэлектрического компонента TE. Проверка конкретной сборки остаётся обязательной.

Низкий заряд включает источники, высокий выключает; между порогами состояние
сохраняется. При старте в среднем диапазоне контроллер не меняет генерацию до
первого достижения порога. Сбрасываемые нагрузки отсортированы:
1 — дорогое производство, 2 — основное производство без owners, 3 — маскировка
и второстепенные модули. У каждой нагрузки заданы HAL-команды `on` и `off`.
Восстанавливаются только нагрузки, отключённые этим контроллером, в обратном
порядке. Возвращение owner сразу восстанавливает группу 2. Если присутствие owner
неизвестно, группа 2 не отключается. Ошибка одного канала не мешает остальным.
Порт телеметрии шины — 27103; UI-модель остаётся на целевом контроллере.

Проверки непосредственно на корабле: [docs/ingame_checks.md](docs/ingame_checks.md).
